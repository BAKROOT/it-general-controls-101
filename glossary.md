# Glossary

Plain-English definitions of every term and acronym used in this knowledge base. One line each. When a chapter uses a term for the first time it should link back here.

| Term | Plain-English definition |
|------|--------------------------|
| **Application control (ITAC)** | A control built *inside* a specific application that keeps individual transactions accurate, complete, and valid (e.g., a 3-way match). |
| **Access review (UAR)** | A periodic check that everyone who can get into a system still should — see *User Access Review*. |
| **Audit trail / log** | A time-stamped record of who did what in a system, used as evidence that controls operated. |
| **Backup** | A saved copy of data that can be restored if the original is lost or corrupted. |
| **Change management** | The controlled process for making changes to systems so nothing breaks unexpectedly or slips in unapproved. |
| **COBIT** | *Control Objectives for Information and Related Technologies* — a framework mapping IT governance objectives to practices. |
| **Compensating control** | An alternative control used when the ideal one isn't feasible, giving similar assurance. |
| **COSO** | *Committee of Sponsoring Organizations* — the framework defining the "why and what" of internal control. |
| **Deficiency** | A control that is missing or not working as intended. |
| **Deprovisioning** | Removing a user's access when they leave or change roles. |
| **Design effectiveness** | Whether a control, *as designed*, would prevent or catch the problem it targets. |
| **Detective control** | A control that finds problems after they happen (e.g., a log review). |
| **Emergency change** | An urgent fix pushed quickly, with approvals documented right after instead of before. |
| **Entity-level control** | A high-level, organization-wide control (e.g., tone at the top, IT policies) that sets the environment for everything else. |
| **Evidence** | Proof a control ran: tickets, approvals, screenshots, logs, reports. |
| **GRC** | *Governance, Risk, and Compliance* — the discipline (and job field) of managing these together. |
| **ITAC** | *IT Application Control* — see *Application control*. |
| **ITGC** | *IT General Controls* — the foundational controls over IT that support everything running on it. |
| **ITIL** | *Information Technology Infrastructure Library* — a set of IT service-management (operations) best practices. |
| **Least privilege** | Give each person only the access they need to do their job — nothing more. |
| **Logical access** | Electronic access to systems and data (logins, permissions), as opposed to physical access. |
| **Material weakness** | The most serious control deficiency — a reasonable chance a material misstatement wouldn't be caught. |
| **MFA** | *Multi-Factor Authentication* — proving identity with two or more factors (password + phone code, etc.). |
| **NIST CSF** | *National Institute of Standards and Technology Cybersecurity Framework* — a security framework (Identify, Protect, Detect, Respond, Recover). |
| **Operating effectiveness** | Whether a control *actually ran* consistently over the period, not just whether it's well designed. |
| **Population** | The complete set of items a control applies to (e.g., all changes in the year), from which samples are drawn. |
| **Preventive control** | A control that stops a problem before it happens (e.g., blocking a deploy without approval). |
| **Privileged access** | Powerful "admin/superuser" access that can change configurations, other users' rights, or data directly. |
| **Provisioning** | Granting a user the access they need, ideally based on their role and an approval. |
| **RBAC** | *Role-Based Access Control* — assigning access by job role rather than person by person. |
| **RCM** | *Risk-Control Matrix* — a table linking each risk to the control that addresses it and how it's tested. |
| **Reliance** | When an auditor trusts an automated control (and does less manual testing) because ITGC is strong. |
| **Remediation** | Fixing a deficiency and proving the fix works. |
| **SDLC** | *System Development Life Cycle* — the controlled process for building or buying and implementing new systems. |
| **Segregation of duties (SoD)** | Splitting a sensitive process across people so no single person can both cause and hide a problem. |
| **Significant deficiency** | A deficiency serious enough to merit attention by those responsible for oversight, but less severe than a material weakness. |
| **SOX** | The U.S. *Sarbanes-Oxley Act* of 2002; **Section 404** requires management (and auditors) to assess internal controls over financial reporting. |
| **Three lines of defense** | A model: 1st line = operations/control owners, 2nd line = risk/compliance, 3rd line = internal audit. |
| **UAR** | *User Access Review* — periodically confirming each user's access is still appropriate. |
| **Walkthrough** | Following one transaction end to end to confirm a control works as described. |
